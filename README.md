# Nic

> 一个仓库内的项目意图账本。

`Nic` 是一个运行在仓库内的项目规划工具。它帮你把项目想清楚，用结构化的方式记录目标、阶段和依赖，让项目不会做着做着就偏航。

它不替代 git，不替代 issue tracker。它只做一件事：**记录你为什么做、做到哪、砍了什么，以及接下来该做什么。**

本地优先，纯文本，git 友好。轻量，按需，不强制。

---

## 为什么需要 Nic

项目最常见的死法不是技术难题，而是**偏航**：

- 目标漂移：做着做着忘了最初要解决什么
- 范围膨胀：功能越加越多，永远发不出
- 决策丢失：三个月后不记得为什么这么选
- 任务脱节：commit 和最初的目标对不上
- 进度失真：以为快完了，其实差很远

现有工具各自只覆盖一部分：git 管代码不管意图，issue tracker 管任务不管全局。

`Nic` 把项目意图直接放进仓库，和代码一起版本化。它用结构化的图回答三个问题：

1. **这个项目由哪些部分构成？**（节点 + 边）
2. **现在做到哪了？**（状态）
3. **为什么这么选？**（决策日志）

## 设计理念

### 项目是图，不是列表

待办列表是线性的，做完就删。但真实项目不是线性的：

- 有些事必须等另一些事做完才能开始。
- 有些事是多个目标的共同前置。
- 有些事做到一半被砍掉，但砍掉的决定比完成更重要。
- 有些事同时服务于多个目标。

这些关系用列表表达不了。列表只能告诉你"还有什么没做"，不能告诉你"为什么还没做""做完这个能解锁什么""砍掉这个会影响什么"。

**Nic 用图表达项目。** 节点是目标或阶段，边是包含和依赖。你看到的不只是"还有什么没做"，而是"整个项目长什么样，我在哪，下一步能做什么，砍掉什么会断掉什么"。

### 意图和代码必须在一起

代码和意图是两套历史：

- **代码历史**：git 管。谁改了什么，什么时候改的。
- **意图历史**：没人管。为什么做这个功能，为什么砍那个功能，为什么选这个方案。

大多数项目只有代码历史。三个月后回头看，你知道代码变成了什么样，但不知道**为什么**变成这样。决策的上下文丢失了，同样的问题会再犯一次。

`Nic` 把意图历史放进 `.nic/`，和代码一起提交。当你 checkout 到三个月前的 commit，你看到的不只是当时的代码，还有当时的目标、阶段和决策。**意图和代码在同一个时间线上。**

### 包含和依赖是两种关系

大多数工具把"属于"和"依赖"混在一起。这是很多混乱的根源。

- **包含**：A 里面有 B。这是结构关系。goal 包含 stage。
- **依赖**：A 做完才能做 B。这是顺序关系。stage 依赖 stage。

两者完全不同：

- 包含是静态的，依赖是动态的。
- 包含决定"谁在谁的范围内"，依赖决定"谁先谁后"。
- 一个节点可以属于多个父节点（共享节点），但依赖通常只在同级之间。

**Nic 用两种边分别表达。** `contains` 管归属，`depends` 管顺序。两者独立，互不干扰。这样你可以自由地移动节点、共享节点、嵌套节点，而不影响依赖关系。

### 数据是契约，界面是壳

一个工具最容易犯的错误是：把业务逻辑写在 UI 里。结果换一个界面就要重写一遍逻辑，加一个新视图就要复制一份代码。

Nic 的做法是：

- **所有逻辑在核心层**（Go）。数据读写、图算法、状态推导、查询，全部在这里。
- **所有输出支持 JSON**。任何界面都能拿到完整的、机器可读的数据。
- **界面只是渲染层**。CLI、TUI、GUI、IDE 插件，都只做三件事：调核心、拿 JSON、渲染。

这意味着：

- 加一个新界面不改核心。
- 换一个界面不改数据。
- 同一个界面可以有多种渲染风格。
- 第三方可以基于 JSON 做自己的界面。

**核心稳了，界面随便换。**

### 先记录，再整理

大多数项目管理工具强迫你在开始之前就建好完整的结构：建项目、建里程碑、建任务、设依赖、分配负责人。这套流程对轻量项目来说太重了。

真实的工作流是反过来的：

1. 先冒出一个想法。
2. 想法慢慢变多。
3. 发现有些想法是相关的。
4. 把它们归纳成一个更大的目标。
5. 再发现有些目标是相关的。
6. 把它们归纳成一个计划。

**Nic 支持这个自下而上的过程。**

- 想法先以独立 goal 存在，不强迫你建 plan。
- 等 goal 多了，再建 plan 把它们归纳起来。
- goal 可以随时加入或离开 plan，不影响 goal 本身。

不强迫用户一开始就规划好。**先记录，再整理。** 结构是长出来的，不是设计出来的。

### 递归结构，无限粒度

Nic 的数据模型只有两个原语：节点和边。plan、goal、stage、子 stage，都是同一个递归模式在不同粒度上的实例。

这意味着：

- 你不需要理解四种不同的结构，只需要理解一种。
- 粒度由你决定。想粗就粗，想细就细。
- 加新层级不需要改数据模型。
- 同一个渲染逻辑可以处理所有层级。

**一个模式，无限粒度。**

### 纯文本，本地优先

Nic 的数据全部是 JSON 和 JSONL：

- **人类可读**：打开文件就能看懂，不需要专用工具。
- **git 友好**：diff 清晰，冲突可以手动解决。
- **本地优先**：数据在你自己的机器上，不依赖服务器，不需要账号。
- **可手动编辑**：如果你不满意 CLI 的输出，直接改 JSON 也行。
- **向后兼容**：JSON 格式不会因为版本升级而失效。

**你的数据是你的，不是我的。**

### 按需，不强制

Nic 不预设你是谁，不预设你的项目有多大，不预设你用多少功能。

- 只有一个 goal？可以。
- 有十个 goal，不需要 plan？可以。
- 有 goal 也有 plan？可以。
- 一个 stage 属于多个 goal？可以。
- stage 嵌套 stage？可以。
- 只用 CLI，不要 TUI 和 GUI？可以。
- 只要 JSON 输出，自己写界面？可以。

**功能在那里，用不用由你决定。** Nic 不替用户做选择，不强迫用户走某条路。

同一个工具，可以是一个人的速记本，也可以是一个小团队的协作基础。规模不同，用法不同，但核心模型不变。

### 轻量规则，自由组合

Nic 的规则很少：

- 数据是节点和边。
- 包含和依赖分开。
- 纯文本，git 友好。

除此之外，没有"必须"：

- 不强制你建 plan。
- 不强制你设依赖。
- 不强制你记录决策。
- 不强制你用某个界面。

**规则轻，自由多。** 你觉得需要就用，不需要就不用。Nic 不做你的老师，不做你的老板，只做你的工具。

### 宇宙比喻

Nic 的显示层可以用宇宙来理解：

```text
宇宙          →  整个项目空间
星系（plan）  →  一组相关的 goal
恒星（goal）  →  一个最终目标
行星（stage） →  目标下的一个阶段
卫星（子stage）→  阶段下的子阶段
```

这个比喻不是数据模型的一部分，是**显示层的语言**。数据层只有节点和边，宇宙比喻是给用户看的。这样数据保持中性，显示层保持直观。

## 安装

```bash
go install github.com/qiuxile/Nic@latest
```

需要 Go 1.22+。或者从源码构建：

```bash
git clone https://github.com/qiuxile/Nic.git
cd Nic
go build -o Nic .
```

## 快速开始

```bash
# 在当前目录初始化 Nic 仓库
nic init

# 添加一个目标
nic goal add "v0.1 CLI 核心" --id v0.1

# 在目标下添加阶段
nic stage add "实现 init" --goal v0.1
nic stage add "实现 goal add/list" --goal v0.1 --after init
nic stage add "实现 stage add/list" --goal v0.1 --after goal
nic stage add "实现 tree 输出" --goal v0.1 --after stage

# 查看科技树
nic tree --goal v0.1

# 标记阶段完成
nic stage done init

# 输出机器可读的图
nic graph --json
```

## 命令

### 仓库

| 命令       | 作用                        |
| ---------- | --------------------------- |
| `nic init` | 在当前目录创建 `.nic/` 仓库 |

### 目标（goal）

| 命令                             | 作用         |
| -------------------------------- | ------------ |
| `nic goal add <title> --id <id>` | 添加一个目标 |
| `nic goal list`                  | 列出所有目标 |
| `nic goal show <id>`             | 查看目标详情 |

### 阶段（stage）

| 命令                                                         | 作用               |
| ------------------------------------------------------------ | ------------------ |
| `nic stage add <title> --goal <id> [--id <id>] [--after <id>]` | 在目标下添加阶段   |
| `nic stage list --goal <id>`                                 | 列出目标下的阶段   |
| `nic stage start <id>`                                       | 标记为进行中       |
| `nic stage done <id>`                                        | 标记为完成         |
| `nic stage cut <id> --reason <text>`                         | 砍掉阶段，记录原因 |

### 视图

| 命令                   | 作用                     |
| ---------------------- | ------------------------ |
| `nic tree --goal <id>` | 以缩进树形式显示阶段依赖 |
| `nic status`           | 按目标分组显示当前状态   |
| `nic graph --json`     | 输出机器可读的完整图     |

### 决策

| 命令                                              | 作用             |
| ------------------------------------------------- | ---------------- |
| `nic log <text> [--stage <id>] [--reason <text>]` | 追加一条决策记录 |

## 数据模型

`Nic` 的数据层只有两个原语：**节点**和**边**。

### 节点

每个节点有：

| 字段      | 说明                               |
| --------- | ---------------------------------- |
| `id`      | 唯一标识，短字符串                 |
| `type`    | `goal` 或 `stage`                  |
| `title`   | 人类可读的标题                     |
| `status`  | `todo` / `doing` / `done` / `cut`  |
| `goal`    | stage 所属的 goal（goal 本身为空） |
| `created` | 创建时间                           |
| `done`    | 完成时间                           |
| `reason`  | 砍掉的原因（仅 `cut` 状态）        |

### 边

每条边有：

| 字段   | 说明                    |
| ------ | ----------------------- |
| `type` | `contains` 或 `depends` |
| `from` | 起点节点 ID             |
| `to`   | 终点节点 ID             |

- `contains`：包含关系。goal 包含 stage。
- `depends`：依赖关系。stage 之间、同级的先后顺序。

**包含和依赖彻底分离。** 这是 Nic 数据模型的核心。

### v0.1 的范围

v0.1 只做两层：

```text
goal
└── stage
    └── stage
        └── ...
```

- 只有 `goal` 和 `stage` 两种节点。
- `depends` 只在同一个 goal 下的 stage 之间使用。
- 没有 plan，没有跨 goal 依赖，没有共享节点。

后续版本会加入：

- **plan**：可选的组织层，把多个 goal 归纳成一个星系。
- **共享节点**：一个 stage 属于多个 goal。
- **嵌套**：stage 可以包含子 stage。
- **GUI / TUI / IDE 插件**：同一份数据的其他视图。

## 仓库结构

`Nic init` 会在当前目录创建 `.nic/`：

```text
.nic/
├── config.json          # 仓库配置：版本、项目名、创建时间
├── graph.json           # 核心：节点 + 边
├── decisions.jsonl      # 决策日志，追加写
└── commits.jsonl        # commit 与节点的关联，追加写
```

**`config.json`**

```json
{
  "version": 1,
  "project": "Nic",
  "created": "2026-10-07T10:00:00Z"
}
```

**`graph.json`**

```json
{
  "version": 1,
  "nodes": [
    {
      "id": "v0.1",
      "type": "goal",
      "title": "v0.1 CLI 核心",
      "status": "doing",
      "created": "2026-10-07T10:00:00Z"
    },
    {
      "id": "init",
      "type": "stage",
      "title": "实现 init",
      "status": "done",
      "goal": "v0.1",
      "created": "2026-10-07T10:01:00Z",
      "done": "2026-10-07T11:00:00Z"
    },
    {
      "id": "goal",
      "type": "stage",
      "title": "实现 goal add/list",
      "status": "doing",
      "goal": "v0.1",
      "created": "2026-10-07T10:02:00Z",
      "done": null
    }
  ],
  "edges": [
    { "type": "contains", "from": "v0.1", "to": "init" },
    { "type": "contains", "from": "v0.1", "to": "goal" },
    { "type": "depends", "from": "goal", "to": "init" }
  ]
}
```

**`decisions.jsonl`**

```jsonl
{"time":"2026-10-07T10:10:00Z","stage":"init","text":"决定用 cobra 而不是标准库 flag","reason":"需要子命令"}
```

**`commits.jsonl`**

```jsonl
{"commit":"a1b2c3d","stage":"init","time":"2026-10-07T11:00:00Z"}
```

## 阶段状态

| 状态    | 含义                 |
| ------- | -------------------- |
| `todo`  | 已规划，未开始       |
| `doing` | 进行中               |
| `done`  | 已完成               |
| `cut`   | 已砍掉，必须记录原因 |

砍掉的阶段不会被删除。它保留在图里，标记为 `cut`，附带原因。**砍掉的决定和完成一样重要。**

goal 的状态自动推导：

- 所有 stage 都是 `done` → goal `done`
- 有任何 stage 是 `doing` → goal `doing`
- 全部 `todo` → goal `todo`

## 设计原则

1. **数据人类可读。** JSON/JSONL，无二进制，git diff 清晰，冲突可手动解决。
2. **`.nic/` 随代码提交。** 它是项目的一部分，不进 `.gitignore`。
3. **所有逻辑在 CLI。** TUI、GUI、插件只调 CLI、拿 JSON、渲染。
4. **ID 用短字符串。** `init`、`goal` 比 `1`、`2` 可读，git diff 友好。
5. **包含和依赖分离。** `contains` 管归属，`depends` 管顺序。
6. **先记录，再整理。** 不强迫用户一开始就建好结构。
7. **按需，不强制。** 功能在那里，用不用由用户决定。

## 和其他工具的关系

| 工具          | 管什么   | nic 的定位                     |
| ------------- | -------- | ------------------------------ |
| git           | 代码历史 | 互补：Nic 管意图历史           |
| GitHub Issues | 任务     | 互补：Nic 管全局结构           |
| TODO 注释     | 临时提醒 | 互补：Nic 是结构化、可查询的   |
| 脑图工具      | 思路整理 | 互补：Nic 是版本化、可执行的   |
| ADR           | 架构决策 | 互补：Nic 包含决策，也包含结构 |

Nic 不试图替代任何一个。它补的是"项目意图和代码分离"这个缺口。
